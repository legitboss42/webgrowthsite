# WhatsApp Stage 10 — AI Layer

Status: IMPLEMENTATION COMPLETE ON ISOLATED BRANCH / VALIDATION PENDING

## Product scope

Stage 10 adds a provider-neutral AI layer to the existing Web Growth WhatsApp workspace. It does not create a second inbox or duplicate CRM. AI reads the existing conversation/CRM context and can only mutate business state through explicitly allow-listed server actions.

The stage has two product modes:

1. **AI Assist** — human-controlled drafting and summaries. Nothing generated by AI Assist is sent automatically.
2. **AI Agents** — autonomous handling only after an Active AI Agent is explicitly assigned to a conversation and workspace AI Agents are enabled.

## Provider/runtime architecture

Initial provider transport is Vercel AI Gateway through its OpenAI-compatible Chat Completions endpoint. The application does not depend on the Vercel AI SDK and does not hardwire business logic to one model vendor.

Authentication is server-only and resolves in this order:
- `AI_GATEWAY_API_KEY`
- `VERCEL_OIDC_TOKEN`

No provider credential reaches the browser or Supabase.

### Fail-closed spending controls

Real AI calls require ALL of the following:
- workspace AI `enabled = true`
- provider authentication available
- explicit `monthly_budget_usd > 0`
- daily request limit not reached
- tracked monthly estimated spend below the configured limit

Production migration defaults are intentionally:
- AI disabled
- autonomous Agents disabled
- monthly budget `$0`

Therefore deploying Stage 10 cannot start AI spend by itself.

Usage records store provider, model, input/output tokens and an estimated USD cost when live Gateway model pricing is available. Vercel-side budgets remain an optional second safety boundary.

## Business knowledge

Stage 10 initially uses Postgres full-text search rather than paid embeddings.

Tables:
- `whatsapp_ai_knowledge_sources`
- `whatsapp_ai_knowledge_chunks`

Manual knowledge is split into bounded chunks and indexed with a generated `tsvector` + GIN index. Server-only RPC `search_whatsapp_ai_knowledge` returns matching approved chunks.

Knowledge modes:
- `KNOWLEDGE_ONLY` — default; business facts, prices, policy and promises must be supported by supplied knowledge.
- `KNOWLEDGE_PLUS_GENERAL` — supplied business knowledge remains primary, with general model knowledge allowed only where it cannot invent business-specific facts.

Customer messages, CRM fields and knowledge content are explicitly treated as untrusted prompt data.

Generated replies are inserted into the existing WhatsApp composer for human review. AI Assist never calls the send endpoint directly.

## Sandbox

A saved AI Agent can be tested with a simulated customer message. The sandbox can read the Agent configuration and knowledge, but it receives no live customer conversation and executes no proposed CRM/contact action.

## Autonomous conversation runtime

A conversation has explicit AI state:
- `ai_handling_mode = HUMAN | AI`
- `ai_agent_id`
- `ai_turn_count`
- `ai_last_handoff_at`

Inbound processing order is deliberately:
1. opt-out/campaign safety
2. Stage 6 automation processing
3. Stage 10 automation control-tag bridge
4. if an automation owned the current turn, stop there
5. otherwise let the assigned AI Agent handle the turn
6. otherwise fall through to the existing safe-reply behavior

This prevents Stage 6 and Stage 10 from sending two replies to the same inbound message.

Autonomous AI also fails closed when:
- AI/Agents are disabled
- contact is opted out
- conversation is human-controlled
- Agent is not Active
- maximum turns are reached
- provider/budget controls block the call
- service window blocks a free-form send

Maximum turns automatically hand control back to a human and require review.

## Human takeover

An authorized workspace member can use **Take over from AI**. This immediately sets the conversation back to human handling and resets the autonomous turn counter. AI cannot resume merely because the old Agent ID remains on the historical conversation row.

## Controlled AI actions

The model never receives arbitrary SQL/database/API access. It returns a strict JSON proposal. The server parses it, removes any action that is not globally supported, removes any action not explicitly enabled for that Agent, and then executes trusted application code.

Supported Stage 10 Agent actions:
- Add tag
- Remove tag
- Change CRM stage
- Update supported contact/custom field
- Add internal note
- Assign conversation to an active team member
- Send a published tracked WhatsApp Flow
- Close conversation
- Request human takeover

Every proposed/executed/rejected/failed AI action is written to `whatsapp_ai_actions`.

## Stage 6 Automation integration

Stage 10 deliberately reuses existing proven Stage 6 **Add Tag** actions instead of modifying the visual workflow runtime/action language during this stage.

Two one-shot control tags are recognized after Stage 6 runs:

### Assign an AI Agent

`AI_AGENT:<agent-slug>`

The slug is the lower-case hyphenated AI Agent name. Example:

`AI_AGENT:web-growth-sales-ai`

If the matching Agent is Active, the latest open conversation is switched to AI handling. The control tag is then removed so a later human takeover remains human-controlled.

The Stage 6 workflow owns the message that created the routing tag. The AI Agent begins with the customer's **next** turn, preventing duplicate replies.

### Generate an internal summary

`AI_SUMMARY`

This asks Stage 10 to create and save a private AI summary for the conversation. The tag is consumed after the attempt so a blocked provider/budget cannot create a retry loop.

This gives Stage 6 native operational interoperability with Stage 10 using an action it already validates, persists and executes reliably.

## Multi-business preparation

AI persistence carries `workspace_scope = 'default'` today. Stage 11 can replace the single-workspace resolver with tenant/workspace IDs without redesigning the AI service boundaries.

## Security

- AI tables use RLS with no browser policies.
- Reads/writes remain server-side service-role operations.
- Provider credentials remain environment-only.
- Same-origin checks protect AI mutations.
- Conversation authorization is reused for Assist and takeover.
- Owner/Manager supervision gates protect AI configuration, Agent management, Knowledge management and sandbox.
- Prompt instructions mark customer, CRM and Knowledge text as untrusted.
- Model output is parsed as data, never executed as code.
- Agent actions are server allow-listed twice: global action list + per-Agent permission list.
- Existing WhatsApp service-window enforcement remains authoritative.
- Existing Stage 6 automation takes precedence on the current inbound turn.

## Production activation rule

Stage 10 may be deployed with AI disabled and a `$0` local budget. This is the safe production default.

A real Owner AI test is a separate deliberate action that requires enabling AI and assigning a non-zero budget. Do not silently enable or spend during deployment/verification.
