01What this is

A WhatsApp Business communication console at /admin/whatsapp, inside the Web Growth marketing site. Internal, password-gated, NOINDEX, never public.

It does three things:

  1. Receives customer messages through Meta's webhook, classifies them into lead intents, and stores them in Supabase.
  2. Displays them across eight console pages.
  3. Sends replies back — text, attachments, voice notes — through the Meta WhatsApp Cloud API, respecting the 24-hour service window.

Read this before changing anything

The backend integration existed and worked before this project started. Almost all of the work has been a reskin, an app shell, and a composer rebuild on top of a working integration — not new plumbing. When in doubt: preserve, don't rewrite.

02Stack, and four truths that surprise people

Stack: Next.js 15.5.14 (App Router, src/ layout), React 18.3.1, TypeScript 5, Tailwind v4, Node 24. Deployed on Vercel. Developed on Windows 11 (PowerShell + Git Bash).

Four things are non-obvious, and not knowing them produces confidently wrong advice.

a. Tailwind v4 has no config file

Design tokens live in an @theme block in src/app/globals.css. There is no tailwind.config.js. Don't add one; don't suggest editing one.

b. There is no Supabase client library in use

Database access is raw fetch against PostgREST with the service-role key, server-side only — src/app/admin/whatsapp/data.ts and src/lib/whatsapp/store.ts. createClient from @supabase/supabase-js is not used. RLS is enabled on the tables with zero policies, so the anon key can read nothing. That is deliberate, and it is why no browser database client exists.

c. There is no realtime — "realtime" is a poll

Because of (b), Supabase Realtime is unavailable. Instead AutoRefresh.tsx polls /api/admin/whatsapp/notifications/ for a cheap digest and calls router.refresh() when the fingerprint changes. It also listens on focus, online, and visibilitychange, and reconciles every 60 seconds so a missed poll can't strand the view. Outgoing messages get an optimistic bubble (OutboundQueue.tsx) reconciled against the stored row by whatsapp_message_id.

If anyone proposes Supabase channels or a websocket, they have missed this.

d. The webhook is the only source of truth for delivery status

Sent / Delivered / Read / Failed all arrive from Meta's status webhook and are written to the database — nothing is manufactured client-side. A monotonic rank is applied inside the PATCH itself, so a late or out-of-order webhook can never walk a status backwards: 

null 0 → accepted|queued|sending 1 → sent 2 → delivered 3 → read 4 → failed 5

03The Meta Cloud API specifics already encoded

Graph version resolves WHATSAPP_API_VERSION → WHATSAPP_GRAPH_API_VERSION → v26.0.

Text is one call: POST /{phone-number-id}/messages. Media is two, which is the part people get wrong: 

1.  POST /{phone-number-id}/media      (multipart)  → { id }
2.  POST /{phone-number-id}/messages  with  type: <kind>, <kind>: { id: mediaId }

Quoting a message adds context: { message_id: <wamid> }.

Media kinds, limits and quirks — encoded in src/lib/whatsapp/media.ts, with tests

Meta silently drops a caption on audio, so the code refuses to attach one rather than pretending. Only document carries a filename.

The typing indicator rides on the read receipt

{ "messaging_product": "whatsapp",
  "status": "read",
  "message_id": "<a REAL inbound wamid>",
  "typing_indicator": { "type": "text" } }

It needs a genuine inbound message id, and it is throttled to one signal every 8 seconds (shouldSendWhatsAppTypingSignal, WHATSAPP_TYPING_REFRESH_MS = 8000). A typing failure must never block a send — it is wired fire-and-forget.

The 24-hour service window

Outside it, Meta refuses free-form messages and only an approved template will go through. The code detects this and surfaces SERVICE_WINDOW_CLOSED → “The 24-hour customer service window is closed. An approved template is required.” Do not engineer around it — abusing the window is how a WhatsApp Business account gets restricted.

04What is built, page by page

All eight pages are live and registered. Nav status lives in src/components/whatsapp/nav.ts — live renders a link, soon renders disabled with a “Soon” chip, so the shell never links to a 404.

The webhook reads these through a 60-second cache and applies keyword overrides after the built-in classifier, so absent settings change nothing.

The composer — the most recent work, commit 82aa9fb

Rebuilt to an approved mockup. ReplyComposer.tsx plus four collaborators:

Editor pill

Auto-resizes one line to four, then scrolls internally. Enter sends, Shift + Enter breaks the line, and it won't steal an IME composition commit. Emoji, paperclip and mic sit inside the pill; the green send button and the + sit outside.

+ → AttachmentMenu

A four-across tile grid (Document, Image, Video, Audio): floating panel on desktop, bottom sheet on mobile. Quick Replies and Templates keep a row below the divider.

EmojiPicker

Tab strip led by a recents tab, green underline on the active tab (emoji glyphs ignore color, so the rule has to carry the state), insertion at the caret, closes on outside click and Escape. Recents persist. No new dependency.

Voice notes

Permission → record → timer → live waveform → cancel / delete / send. The blob posts to /reply/audio/, uploads server-side, and arrives as a real playable WhatsApp audio message.

Reply Mode

ReplyTarget.tsx. A quoted panel above the editor — green rule, author name, truncated excerpt, X — and Escape to leave. A per-bubble reply button reaches the composer through a React context nested inside the outbound-queue provider.

Deliberately not built

The mockup also showed Contact, Location and Camera tiles. The send path cannot produce those message types, so they were left out rather than shipped as dead UI.

The pattern to copy

The quoted wamid originates in a browser, so it is untrusted. Passing it straight into Meta's context would let an authenticated admin quote another conversation's message and leak its content into this customer's chat. resolveSupabaseWhatsAppQuotedMessageId re-checks server-side that the id belongs to this conversation; anything unrecognised falls back silently to the conversation's own latest inbound message. Both reply routes go through it.

Also live: the six “live messaging” features — dashboard logo, WhatsApp business profile picture, customer fallback avatars, agent→customer typing indicator, near-real-time message updates, and delivery statuses.

A real trap in icons.tsx

It evaluates JSX at module level, so any *.test.ts that imports it — directly or transitively — crashes the test runner. That is why every piece of pure logic lives in a separate .ts model module, and why buildWhatsAppReplyQuote takes a structural type instead of importing the page's row type. Keep that separation.

Three migration rules that matter

  1. There is no migration runner. Writing the .sql file does nothing. It has to be pasted into the Supabase SQL editor and run by hand. Always make the code degrade to a documented default until the column exists.
  2. Never run supabase db push. The same folder holds five TikTok scheduler migrations, one of which creates cron jobs. The remote has no CLI migration history, so a push would try to apply those too and cross the do-not-touch boundary.
  3. DATABASE_URL / POSTGRES_URL / PGHOST point at neon.tech, not Supabase. There are two databases in this project. Running a WhatsApp migration against DATABASE_URL creates the table in the wrong database.

A defensive pattern worth knowing

PostgREST rejects an entire select that names a column the table lacks, and readWhatsAppRows collapses that to null — which once would have blanked every thread. readConversationMessageRows now retries without the optional column, so an unapplied migration costs a sentence, never the messages.

WHATSAPP_VERIFY_TOKEN            ← webhook handshake

Vercel marks some variables Sensitive by design, which makes them write-only: vercel env pull writes the literal string [SENSITIVE] and no CLI call can recover the real value. Get the service-role key from the Supabase dashboard → Project Settings → API instead.

Two are missing on this machine entirely

SUPABASE_SERVICE_ROLE_KEY and META_APP_SECRET. This explains a lot of “it looks broken locally”:

  • Every Supabase read returns null, so every data page renders its empty state (“—”) locally. Meta-backed pages — Templates, Phone Numbers — do show real data, because the access token is present.
  • The webhook would reject Meta's signature, and a localhost webhook is unreachable from the internet anyway.
  • No send, delivery status, or realtime behaviour can be exercised end-to-end from this machine. Those paths have unit tests and were checked against a production build, but never observed on a handset. Test them in production, one of each, after any change.

.env.example carries names only. Never commit a real value.

09Commands, and the traps inside them

# Tests — there is NO `npm test` script
npx tsx --test $(find src -name '*.test.ts' -o -name '*.test.tsx')

# Typecheck — there is NO `typecheck` script
npx tsc --noEmit

# Lint — scope it. Bare `npm run lint` walks .codex-temp/ (~814 pre-existing findings)
npx next lint --dir src/app/admin/whatsapp --dir src/components/whatsapp \
              --dir src/lib/whatsapp --dir src/app/api/admin/whatsapp

# Build  =  prepare-build.mjs && validate-sitemap.mjs && next build
npm run build

# Dev
npm run dev

Trap 1 — never build while dev is running

Both write .next/. A production build clobbers the dev server's chunks and every dev request then 500s with Cannot find module './383.js'. It is not a code bug. Fix: stop dev, rm -rf .next, restart. Working order — tests → tsc → lint → stop dev → build → restart dev.

Trap 2 — every new page must be registered

scripts/validate-sitemap.mjs runs inside npm run build and fails on any src/app/**/page.tsx missing from src/lib/route-governance.json. Console pages use: 

{ "path": "/admin/whatsapp/<name>/", "status": "NOINDEX",
  "sitemap": false, "reason": "..." }

API routes and plain components are exempt. Adding WhatsApp entries is safe — publicPages.test.ts asserts only the scheduler entries, which must not be touched.

Traps 3 and 4 — smaller, still sharp

nav.test.ts asserts the exact ordered list of live routes, so promoting a route from soon to live means updating that assertion in the same commit. Nav order is Workspace → Growth → Configuration. And API fetches need trailing slashes: /api/admin/whatsapp/reply/, not …/reply.

Trap 5 — the most important lesson of the whole project

A green build says nothing about whether a dynamic page renders. The shell rendered the wordmark with quality={80}, but next.config.mjs allows only [60, 65, 68, 75]. An unlisted quality makes next/image throw during render. Console pages are server-rendered on demand, so next build never executed that path, and React swallowed the throw into the Suspense fallback. Result: all eight console pages served nothing but the loading screen while build, typecheck, and 572 tests stayed green.

It is now pinned by src/components/whatsapp/shellBranding.test.ts. The moral: after any change to these pages, actually load them and read the HTML.

Icons are local inline SVG

src/components/whatsapp/icons.tsx, not lucide-react. Zero dependency, one stroke weight, one 24×24 box. Add a glyph to both the WhatsAppIconName union and the ICON_PATHS record — forgetting the union is a real typecheck error.

Every mutation follows one shape

client → fetch("/api/admin/whatsapp/<x>/", …)
       → route:  hasWhatsAppAdminAccess(cookieStore)  → 401
                 isSameOriginMutation(origin, url)    → 403
       → store
       → router.refresh()

Both guards run before the body is parsed. Copy this for any new write.

Server components fetch; client components poll

Secrets never cross the boundary — the layout passes a senderConnected boolean to the client shell, never a credential.

Errors are sanitized before an operator sees them

Meta error codes map to fixed sentences (131026, 131047, 131049, 131051, 131053, 132000, 132001, 133010, 470 and 368 are all handled). Raw provider payloads and stack traces are never displayed. console.error logs a status and a Postgres error code — never a token, never the document.

11Security rules — do not break these

  • Meta credentials stay server-side. No access token, app secret, verify token, or service-role key in a client component, and nothing sensitive behind NEXT_PUBLIC_*.
  • Never log a full secret, and never print one into a report or a commit message.
  • The media proxy /api/admin/whatsapp/media/[mediaId]/ exists precisely so the browser can display media without ever seeing the token.
  • Treat every id coming from a browser as untrusted, even from an authenticated admin, and re-check server-side that it belongs to the conversation in hand. resolveSupabaseWhatsAppQuotedMessageId is the pattern.
  • Internal notes must never be sent to WhatsApp. If you extend the composer, keep that mode boundary loud.
  • Do not bypass the 24-hour window. Meta can restrict the business account.

Checked, and not a leak

The Settings page shows the configured WHATSAPP_BUSINESS_ACCOUNT_ID and WHATSAPP_PHONE_NUMBER_ID values to an authenticated admin. Those are identifiers, not secrets — useless without the token, which never leaves the server — and displaying them is the readiness console's whole purpose. Leave it alone.

13Known gaps — what has never been verified

Be honest about these when asking for advice; they change what good advice looks like.

Gap 1

No page has ever been opened in a real browser at multiple breakpoints, and no accessibility audit has been run. Everything is structurally responsive and semantically marked up by inspection — that is not observation. This is the recorded next task.

Gap 2

No send has been observed arriving on a handset. Attachment upload, a voice note playing as WhatsApp audio, the typing indicator reaching Meta, and Sent/Delivered/Read coming back are unit-tested and checked against a production build — but the customer-side half has never been watched.

Gap 3

Stage 9 — conversation notes and labels — is blocked on an additive migration, not on code.

Gap 4

Stages 14 and 15 do not exist. No files, no routes, no nav entries beyond the “Soon” chips.

Cosmetic, pre-existing

The locked screen says “Unlock the voice tool”, because InternalUtilityUnlockForm is shared with a text-to-speech utility. Fixing it properly means a per-utility copy prop on a shared component.

Deliberate

Old inbox bookmarks (/admin/whatsapp/?filter=HOT&lead=…) now land on the Overview and the params are ignored. Add a redirect only if it becomes annoying in practice.

14What to do next

The recorded next task, and the cheapest real win

A browser and accessibility pass over the eight console pages, starting with /admin/whatsapp/settings. 

npm run dev      # then open /admin/whatsapp

Open each page at 375 / 390 / 430 / 768 / 1440 px and exercise:

  • the mobile drawer — open, Escape to close, scroll lock
  • the lead card list on narrow viewports, and the overview chart
  • the three-column conversations layout at each breakpoint
  • the composer: type, Enter, Shift + Enter, grow to four lines then scroll, emoji insert at caret, the + panel as a bottom sheet, record a voice note, enter and leave Reply Mode
  • the settings form's keyboard path — the business-day pills are sr-only checkboxes with the focus ring on the label; verify the ring is actually visible
  • touch targets at roughly 44×44 px

Then run Lighthouse or axe DevTools. This closes Gap 1 and costs less than either feature.

Do this in production too, once

Send yourself one text, one image, one document and one voice note, and watch the status ticks progress. That closes Gap 2, and no amount of local testing substitutes for it.

Then one of two features — a real decision, not a default

Automations · Stage 15 · lighter

Auto-replies and routing rules. Needs a new table plus a decision about where rules execute: inline in the webhook path (simple, but it puts your logic in front of every inbound message, and a bug there loses messages) or in a job/queue (safer, more moving parts). Read src/lib/whatsapp/store.ts end to end before designing anything.

Campaigns · Stage 14 · heaviest

Sends approved templates outbound. Needs a new send path, recipient selection, rate limiting, and consent/opt-out handling. This is the one remaining piece that can get the WhatsApp Business account restricted if done carelessly. Think about opt-out before you think about UI.

Or a quick win instead: unblock Stage 9. Write an additive migration adding notes and labels to whatsapp_conversations, run it in the Supabase SQL editor, then build the panel inputs — keeping the code degrading gracefully until the columns exist.

Context primer 
I'm working on an internal WhatsApp Business console inside a Next.js 15 App Router marketing site (src/ layout, React 18, TypeScript 5, Tailwind v4, Node 24, deployed on Vercel). It lives at /admin/whatsapp and is password-gated and NOINDEX. Please respect these facts about the codebase — they are unusual and they invalidate a lot of default advice:

1. Tailwind v4 with NO tailwind.config.js. Design tokens are in an @theme block in src/app/globals.css. Custom palette ("Growth Ledger"): ledger-deep #0c3327, ledger #124a38, ledger-bright #1c7a54, paper #eff1ec, paper-raised #f7f8f4, ink #14140f, ink-soft #454a3f, ink-faint #737868, rule #d2d6cb, brass #b4802f. 3. "Realtime" is a poll: a client component polls an API digest route and calls router.refresh(), plus focus/online/visibilitychange listeners and a 60s reconcile. Outgoing messages get optimistic bubbles reconciled by WhatsApp message id (wamid).
